# 求职助手桌面应用第一版设计

日期：2026-10-06。状态：界面与三项产品选择已获用户确认；本文记录实施依据。桌面应用尚未实现。

## 目标与确认结果

用户已有简历、个人资料和公司申请表，希望在 Windows 应用中完成资料核对、配置投递、确认本轮授权、查看执行过程和处理招聘回复。八张已确认的界面稿是第一版视觉基准，见 [图册](index.html)。

三项选择均按推荐方案执行：

1. 应用内连接 Codex，直接开始、查看进度、中断和恢复任务。
2. 人工事项在应用中编辑，用户确认具体内容后由执行器发送；面试安排始终由用户决定。
3. 导入文字型 PDF、Word `.docx` 和现有资料 JSON，提取后逐项核对再使用。扫描件提示人工补充；旧 `.doc` 明确提示先转 `.docx`，不伪装解析成功。

Windows、本地单用户、单个可见浏览器执行队列。每轮确认范围后执行；材料、范围改变后重新确认。关闭应用先暂停并保存状态，下次打开不自动继续投递。最小化可以继续，但界面必须明确显示占用桌面；用户使用电脑前可暂停。

## 技术边界

采用 Tauri 2、React、TypeScript、Vite；界面组件采用 shadcn/ui 与 Tailwind。保留 Python 的台账、规则、表格、截图与 computer use 逻辑，SQLite 继续保存业务状态。Python 工作进程用 PyInstaller 打包，不要求普通用户单独安装 Python。

Tauri 原生进程负责子进程生命周期、文件选择、受限 IPC 和桌面通知。React 不直接启动任意命令，也不持有 Codex 登录凭据。Codex App Server 通过 stdio 连接，账号登录交由 Codex 自身管理。适配器隔离其协议变化，不把模型输出文本当成业务成功状态。

Python 工作进程以结构化请求调用已有 `cli.dispatch(store, request)`、`Dashboard`、`panel_state` 等逻辑。模型调用工具时使用随应用提供的执行入口；首个实现里程碑必须验证打包入口、截图查看和桌面输入的完整通路。仅有模型问答成功不能验收执行器。不得为了让演示通过而全局放开权限或修改用户的 Codex 配置。

界面、AI 会话和业务台账分别保存自己的状态：前端负责展示；App Server 管理模型上下文；SQLite 保存授权、动作及结果。`threadId` 与 `run_id` 建立映射。模型回合完成不等于投递完成，恢复模型上下文也不等于允许再次发送。

应用分发包含 Skill 与执行依赖，不要求用户寻找额外 computer-use Skill。已有 Codex 安装先做兼容性检查；缺少 Codex 时通过引导安装经验证版本。Python 侧内置依赖与 Codex 账号登录是两种不同的就绪条件，不能用一个“已安装”状态混淆。

参考：[App Server 官方接口](https://learn.chatgpt.com/docs/app-server)、[Tauri sidecar](https://v2.tauri.app/develop/sidecar/)。本机验证结论见 [接入报告](codex-probe.md)。

## 页面与可验收行为

| 页面 | 主操作 | 第一版完成标准 |
|---|---|---|
| 首页 | 开始官网网申、BOSS 推荐投递、BOSS AI 精筛 | 三个入口清晰，显示资料/账号/执行器就绪状态与待办；有任务才显示真实统计 |
| 个人资料 | 导入、核对、保存 | 显示字段值及原始出处，缺项不臆造；用户确认后的版本用于本轮 |
| 公司网申 | 导入公司表、选择公司、预览授权 | 支持现有 Excel/CSV 解析；不改原表；每家公司选一个最匹配岗位 |
| BOSS 投递 | 选择模式、设置条件与上限 | 推荐模式按平台筛选结果沟通；AI 精筛模式读取详情并按要求判断 |
| 回复规则 | 编辑条件与原话、试匹配 | 条件与回复一起保存；测试显示命中原因；面试规则优先于普通问答 |
| 正在执行 | 查看当前步骤/截图、暂停、接管、恢复、停止 | 队列、动作与结果分开；截图带时间；断线不能继续显示为正常执行 |
| 待我处理 | 编辑、确认发送、明确恢复 | 保存草稿不发送；确认发送不自动解锁；新消息到达后旧确认失效 |
| 投递记录 | 筛选、查看字段/截图、导出 | 成功、失败、待确认都可查；字段值、来源、截图能互相对应 |

保留已批准的整体布局与视觉风格，开发时统一导航、字体、间距、状态标签与图标。新增状态使用现有页面内的提示、抽屉和对话框承载，不增加另一套导航。

## 核心流程

### 首次使用与资料

环境检测 → Codex 登录状态 → 导入简历及个人资料 → 查看提取结果与出处 → 用户确认资料 → 配置任务。文字提取在本机进行；需要模型整理时仅传所需内容，应用明确说明 AI 分析会向模型服务发送资料/截图。本地保存不代表离线推理。

每个字段保存 `value`、`source_file`、`locator`（页码/段落/JSON 路径）。冲突项并列展示并由用户选择；空值维持空值。简历文件只作为用户选择的附件，不自动改写。

### 本轮授权与执行

任务预览同时列出渠道、公司范围/筛选条件、投递模式、数量上限、简历、资料版本和回复模式。确认后保存配置快照与授权原文，再创建 AI 会话。重复点击不能建立重复任务。

官网逐字段记值和出处，切页前截图；长字段分段覆盖。BOSS 推荐模式不要求查看详情，AI 精筛模式按偏好判断；首次沟通使用平台预设话术，对方索要附件才发送指定简历。

继续沿用 `prepare → claim → 操作 → 结果核验 → finish`。成功必须有对应证据；超时、崩溃、找不到回执时标记待核查，禁止自动重试外部发送。成功与失败都导出记录；若未到可填写页面或无法截图，也记录失败原因和缺失证据原因。

### 暂停、关闭与恢复

暂停先持久化业务暂停状态，使输入入口拒绝后续动作，再请求 `turn/interrupt`。服务端返回“没有活动回合”时仍保持业务暂停，核对回合状态并处理启动时序；不能把暂停误显示为失败后自动继续。已经进入系统调用的单个输入可能完成，需观察结果后给出“已暂停”；无法确定的提交记录为待核查。

恢复先检查资料与授权范围，核对未决动作，绑定目标窗口，重新截图。不得复用暂停前画面。关闭和进程异常按相同原则收尾；仅终止本应用启动的子进程。全局桌面锁仍保证只有一个执行器控制鼠标键盘。

持续值守由应用调度器在应用运行、已授权且执行器就绪时触发。无变化不重复通知；应用退出或电脑休眠时不声称仍在观察。达到投递上限后只进入授权范围内的回复检查，不自动重置上限。

### 人工确认发送

待办记录绑定 `conversation_id + message_key`。用户查看最新消息、编辑、预览最终文字并点击确认发送。后端建立一次性发送授权，绑定用户确认的原文哈希及当前消息版本。

现有自动回复路径禁止在人工锁定会话中执行，因此需要独立的人工发送入口，不能临时把会话改为自动。该入口仍检查轮次、接收人、最新消息、一次性授权、执行锁和截图，并走相同动作台账。确认内容变化、对方新消息、重复点击、过期授权均阻止发送。

核验聊天气泡后记录发送成功；无法核实则待核查。发送后会话继续锁定，只有用户另行点击“恢复自动处理”才解除。面试邀约与薪资混合在同一条消息时，整条转人工。

## 数据与兼容

复用现有 `records.sqlite3` 与证据文件结构。新表保存资料版本、会话映射和人工发送授权；迁移前备份，失败回滚，原资料及证据不删除。图片按记录 ID 受限读取，不开放任意路径。支持明确选择旧数据目录，不能静默合并两份台账。

既有 Skill/CLI 保持可用；桌面专用入口通过小型适配层复用领域逻辑，不复制整份 `store.py` 或 `policy.py`。资料、截图、凭据、临时请求和个人导出不进入源码或发布包。

## 发布门槛与本轮边界

第一阶段验收对象是应用内完整模拟流程：资料 → 授权 → 填写/沟通 → 截图 → 暂停恢复 → 面试人工回复 → 结果导出。随后才在用户选择的真实网站、明确范围内验证。真实 BOSS 和不同 ATS 兼容性仍待验证。

第一版不做云同步、多人权限、手机端、无人登录、扫描件 OCR、自动修改简历、全站通用承诺或后台系统服务。自动更新可后续加入；先确保安装、手动升级和数据保留。

开发机当前 PATH 未发现 Rust/Cargo；Tauri 构建还需核验 Rust、MSVC 和 WebView2。当前接入探针只验证了模型协议，没有验证这些构建依赖。
